# `.pic` 数据解析调研记录

调研日期：2026-08-07
调研对象：某磷酸铁锂产线的一批 DCS 工程数据（82 个 `.pic` 流程图 + 一份工程备份 zip）
调研目的：确认这批 `.pic` 数据能否解析、用什么工具解析、解析出来对时序平台有什么价值

> 本文中的位号、描述与路径均已脱敏，换成了**结构同形的虚构样例**
> （如 `P1_PT100101A01_PV`）。格式规格、解码逻辑与实测数量级统计均为真实数据。

---

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 这是什么 | **中控技术 SUPCON DCS** 操作站流程图，私有二进制格式 `SDFF` |
| 有现成开源解析器吗 | **没有**（已搜证） |
| 能解析吗 | **能**。格式已完全逆向，82/82 文件解析成功 |
| 需要什么依赖 | 解析器纯 stdlib（`struct` + `zlib`）；读点表需 `access_parser` |
| 最有价值的产物 | 12,012 个位号 + 50,877 条点表字典（中文描述 / 量程 / 单位 / 六级报警限） |

## 2. 溯源：这批数据是什么

初始只知道是「流程图」目录下的 `.pic` 文件，`file` 命令识别为 `data`。

**厂商识别的关键证据**（都在同级的「其他信息」目录）：

1. 一份文本文件里写着该 DCS 的操作站账号与口令，口令是厂商默认值的形式
2. 一个工程备份 zip，解开是 `SUPCON_PROJECT/` 目录树

由此确认为 **SUPCON（浙江中控技术）WebField 系列 DCS** 的工程数据。流程图由
配套组态软件 **SCDrawEx**（AdvanTrol-Pro / VxControl 软件包的一部分）产生。

> ⚠️ **拿到这类工程包时顺手检查一下**：DCS 操作站口令以明文形式跟工程数据放在
> 同一个共享目录里是常见情况。如果口令还是厂商默认值，值得向现场提示更换，
> 并收敛该目录的访问范围。

## 3. 格式逆向过程

完整规格见 [format-spec.md](format-spec.md)，这里只记录**推导链与踩过的坑**。

### 3.1 容器层

`xxd` 头部立刻看出结构：魔数 `SDFF`，随后是 UTF-16LE 的流名
（`DocInfo` / `PageInfo` / `Shape` / `Tag` / `Text`），每条目录项 0x80 字节对齐。

目录项里 `offset` / `flag=1` / `uncompressed_size` 三个 u64 的位置靠交叉验证确定：
用 `size` 字段与「下一个流的 offset 减本 offset」对比，压缩比在 1.05×～15× 之间，
符合 zlib 对结构化数据的表现。

**坑 ①**：负载开头 4 字节是重复的未压缩长度，`zlib.decompress(data[offset:])` 会
直接失败，必须 `data[offset+4:]`。

### 3.2 属性树层

解压后 `strings` 只能看到 `DocInfo` / `PageInfo` / `Shape` / `Text` 四个词，
其余是高熵数据——一开始误判为二次加密。实际是**紧凑的 TLV 属性树**，
字符串短且是 GBK，所以 `strings` 认不出来。

以最小的 `DocInfo`（51 字节）为突破口逐字节对齐：

```
33 00 00 00                     总长度 = 0x33 = 51 ✓ 等于流长
10 76 65 72 73 69 6f 6e 00      type=0x10 "version"
00 32 00 00                     int32
10 66 69 6c 65 54 79 70 65 00   type=0x10 "fileType"
00 00 00 00                     int32 = 0
02 74 65 6d 70 6c 61 74 65...00 type=0x02 "templateName"
01 00 00 00  00                 u32 长度=1 + 1 字节（空串的 NUL）
00                              流终止符
```

类型码随后靠 `PageInfo` 里的自解释字段确认：`nRefreshTimer` = `f4 01 00 00` = 500ms、
`bFullscreen` 是单字节、`centerX` 是 double。

**坑 ②（最耗时）**：容器的 `size` 字段**从自身起算**，且末尾有 `0x00` 终止符。
第一版按「size = 子记录字节数」实现，`Text` 流对不上 4 字节，`Shape` 流则在几百
字节之后才炸出「未知类型码 0x0e」——错位的**表现位置离起因很远**，容易误以为是
新类型码而不是偏移错误。靠 `Text` 流（结构最简单、末尾两个连续 `0x00` 清晰可见）
反推出正确关系。

**坑 ③**：`0x05` 数组的长度字段后有 1 个额外 flag 字节。表现同样是「后续解析出
奇怪的类型码」——`clsid` 声明 16 字节却消耗了 17 字节。

### 3.3 验证

对全部 82 个文件跑通，无未知类型码、无残留字节。这是格式正确性的强证据：
错误的偏移假设在 28,521 个图元里几乎不可能一次都不暴露。

## 4. 工具选型

| 方案 | 可行性 | 评价 |
|---|---|---|
| 官方 SCDrawEx（AdvanTrol-Pro / VxControl） | 可用 | 最权威，但 Windows + 需授权，**无法批量自动化**，不适合入数据管线 |
| 现成开源 `.pic` 解析器 | ❌ 不存在 | 已搜证，只查到官方工具的存在，无格式规格与第三方实现 |
| **自研 SDFF 解析器** | ✅ 已验证 | 纯 stdlib，~200 行，82/82 通过。**本项目采用** |
| `access_parser` 读点表 | ✅ 已验证 | 纯 Python 读 Access Jet DB，无需 ODBC/Windows |
| `mdbtools` 读点表 | 可用 | 需 `apt install`，功能等价，但引入系统级依赖 |
| 截图 + OCR | ⚠️ 最劣 | 位号、量程、报警限全部丢失，只剩像素 |

搜证记录：以「SUPCON 中控 DCS .pic 流程图文件 格式 解析 组态」检索，结果只确认了
SCDrawEx 作为官方流程图制作软件存在，**没有任何 `.pic` 格式规格、解析实现或
第三方工具**。相关链接见文末。

## 5. 实测数据规模

### 5.1 流程图（82 个 `.pic`）

| 指标 | 数值 |
|---|---|
| 流程图页 | 82（zip 工程内另有 383 个） |
| 图元总数 | 28,521 |
| **唯一位号** | **12,012** |
| 位号引用总次数 | 16,394 |
| 图元级位号绑定 | 4,708（`strDLTag` 4,651 + `strTag` 57） |
| 唯一中文标签 | 2,297 |
| 画布尺寸 | 1920×960 |

工段划分（目录即工艺分段）：

```
1 原料精准配比 / 2 湿法研磨 / 3 喷雾干燥 / 4 高温气氛烧结
5 烧结块体破碎、气流粉碎 / 6 多级除磁及成品包装 / 7 辅助公用
```

位号命名前缀以 `P1_` 为主（11,459 个），另有 `P1ZSXJL_` / `P1ZSX_` / `FIQ_` 等。

### 5.2 工程点表（zip 内 14 个 `Tags.mdb`）

路径：`SUPCON_PROJECT/<工程名>/Control/CA0/CS<NN>/Tag/Tags.mdb`
格式：Microsoft Access **Standard Jet DB**，每个控制站一个。

**合计 50,877 个位号**，含中文描述。表结构见 [tag-database.md](tag-database.md)。

### 5.3 关键验证：流程图 ↔ 点表覆盖率

```
流程图位号 12,012 个 -> 命中点表 11,810 个 (98.3%)
```

未命中的 202 个全部是 `ani` 组里的**表达式**而非位号：

```
P1_2_M100601F_AOL OR P1_2_UF100601B_A
P1_3_HV100701A_K + 2 * P1_3_HV100701A_G
```

即**真实位号的覆盖率实际接近 100%**，两份数据可以可靠 join。

## 6. 能拿到什么

### 6.1 位号 → 中文描述

```
P1_PT100201B_3.PV        -> 出口压力
P1_PA100301A_GDF_OFF_X01 -> 输送管道阀XV01关到位
P1_WA100401B_DI_PLF_C.PV -> P1-WA100401B中间料仓排料阀关到位
P1_3_SF100501A_ENA       -> 进口伺服使能
```

### 6.2 工程量程与报警限

`AI` 表提供 `EU`（单位）、`SCL`/`SCH`（量程上下限）、六级报警限
`LLL`/`LL`/`L`/`H`/`HH`/`HHH` 及各级报警等级与描述，另有 `HYS`（死区）、
`TFLT`（滤波时间）。

### 6.3 空间与拓扑

每个 `DataLink` 图元带位号 + 屏幕坐标，可与静态中文标签做**就近匹配**，
拿到位号的现场语义（`P1_LT100105` 旁边写着「纯水液位计」）。

> 就近匹配是启发式，有噪声——同一区域标签密集时会匹配到相邻设备。
> 本项目默认设 200px 距离上限，超出即留空：**错误的标签比没有标签更有害**。
> 需要高置信度语义时应优先用点表的 `Tag_Desc`，就近标签只作补充。

`PolyLine` / `arCurve` 图元记录管道走向，可用于推导设备上下游关系。
格式本身**不显式存储连接拓扑**，需要从几何推，这部分未做。

### 6.4 控制逻辑接线（`LogicPic`，同格式复用）

工程 zip 的 `Control/CA0/CS<NN>/LogicPic/` 下有 **218 个 `.pic`**，
是组态软件画的**控制逻辑图**，不是操作站画面。

**它们是同一个 SDFF 格式，本解析器零改动即可解析。**已实测确认。

解析一张变频调节回路的逻辑图，`Text` / `Tag` 流给出功能块及其**引脚级接线**：

```
块类型 : PIDEX
引脚   : BKIN  BKINERR  PV  PVERR  MV  BKOUT  BKOUTERR
接线   : P1_YHIC_PC100101A.BKOUT  ->  P1_HIC_PC100101A.BKIN
         P1_HIC_PC100101A.{PV, PVERR, MV, BKOUT, BKOUTERR}
```

这是 §6.3 那条「格式不存连接拓扑」的**例外**：操作站画面里连接关系确实只能从
几何推，但控制逻辑图里连接关系是**显式写出来的**——引脚名 + 位号引用成对出现。

价值上这比几何推导的管道拓扑高一个量级：几何给的是**物理连通**，
逻辑图给的是**控制因果**（谁的输出接谁的输入、跳车联锁怎么传播）。

**边界（重要）**：逻辑图给的是**块类型 + 接线**，**不含整定参数**。
已核对点表 `FB` 表的列（`Property_ID`/`FBType`/`ModuleID`/`ProgName`/`Address`/…）
——**没有 PID 参数列**，`RefParam` 表为空。要拿 PB/TI/TD 得另找来源，
候选是同批未解析的 `.fbd`（见 §10）。

## 7. 对时序分析的价值

做 DCS 时序数据的异常检测 / 工况分析时，这批元数据能补上两层通常缺失的东西：

1. **位号 → 中文描述字典（50,877 条）—— 语义层**
   时序库里的 measurement 名往往就是裸位号（`P1_PT100201B_3`），
   不论是人还是模型都读不出物理含义。这是一份来自工程组态的权威翻译表。

2. **量程与六级报警限 —— 工程先验**
   `SCL`/`SCH` 可直接用于归一化基线；`LL`/`L`/`H`/`HH` 是现场工程师已经组态好的
   阈值，可作为**异常标注规则的候选**，省掉大量人工标注。
   （注意判读时要同时看 `EN*` 使能位，见 [tag-database.md §3.3](tag-database.md)。）

3. **工段分组 —— 结构层**
   页面归属天然给出位号的工艺分段，是工况分析与异常传播定位的结构化输入。

⚠️ 这些是**调研结论**，不是已验证的结果。真正接入前还需要确认两件事：
位号与时序库里实际 measurement 的命名是否一致、点表的报警限是否与现场运行值同步。

## 8. 最大的坑：`access_parser` 会毁掉 28% 的中文描述

这是整个调研里最有价值、也最容易被漏掉的发现，因此单列一节。

**直接用 `access_parser` 读点表，28.27%（14,385 / 50,877）的 `Tag_Desc` 是坏的。**

成因是 Jet4 字符串里的 `0x00` 是**压缩/非压缩模式切换符**而非数据，
`access_parser` 把它当作要清除的 NUL 删掉了。详细机理与修复见
[tag-database.md §5](tag-database.md#5-坑access_parser-的-jet4-文本解码是坏的)。

**这个坑之所以危险，是因为它有一部分是"静默"的**：

```
'DCS供给时间设定值'  →  'DCS\x00\x9bOÙ~öeô\x95¾\x8b\x9a[<P'   一眼可见是乱码
'CV01光电'           →  'CV01IQ5u'                             看起来完全正常
```

后一种形态不会被任何乱码检测发现，会直接当作有效描述流进下游。
如果拿这份字典去做位号语义标注，污染是隐蔽且不可追溯的。

### 排查过程中的一次错误结论

中途曾判断成因是「`access_parser` 把 GBK 字节按 UTF-16 解错」，并写了一版
「事后回编重解」的启发式修复。**这是错的**——该方案对已丢失 NUL 的
`CV01IQ5u` 根本无解，而且实测跑下来一行都没修好。

真因是抓了实际字节才定位到的。教训：**编码问题不要靠观察结果串猜，
要拿到进解码器之前的原始字节。**

本项目 `tagdb.decode_jet4_text()` 实现了正确的切换符逻辑，修复后可疑行降到 0。

## 9. 后续验证：配对的时序数据存在，只是不在本批交付里

§7 说这批元数据能给时序分析补语义层与工程先验。**该结论成立，配对数据也确实存在**
——只是不在本批交付物里，要另行接入时序库。

这一节记过两次核对，第二次推翻了第一次。两次都保留，因为出错的方式比结论更值得记。

### 9.1 第一次核对（结论错误，已作废）

解析完工后立刻做了一次配对检查，当时判定「配不上任何时序数据」。依据两条：

1. **原始数据目录名就写着「时序数据除外」**——整批交付物只有流程图与工程组态。

2. **手边用于异常检测评测的黄金数据集来自另一家厂**。它的测点命名是另一族，
   与本工程点表取交集：

   ```
   黄金数据集测点 50 个 -> 落在 SUPCON 点表里的: 0
   ```

   命名体系完全不同族，不是「同一批点换了个写法」，是两家不同的厂。

两条证据**本身都成立**。错在推论：只核对了「手边现成的那个评测数据集」，
就下了「没有任何配对时序数据」的全称判断。

### 9.2 第二次核对（订正）

该厂自己的历史时序数据在一个独立的 IoTDB 实例里，与本批交付物分开存放；
而**它的测点导入清单就随交付物一起放在数据根目录**（一份配置 JSON，
1.1 万条测点），第一次核对时没去看。

把流程图抽出的位号与该清单取交集：

| | |
|---|---|
| 流程图抽出的唯一 `base_tag` | 3,681 |
| 落在该厂时序库测点清单里的 | **3,536（96.1%）** |
| 其中主装置前缀的位号 | 3,388 → 命中 **3,281（96.8%）** |

未命中的 145 条主要是画面内部变量与拼接表达式（`*_copy1` 副本、HMI 中间量），
不是真实测点——与 §5.3 里流程图 ↔ 点表未命中的成因一致。

**订正后的含义**：缺的既不是工具也不是数据，而是**接入**——把解析出的位号字典
与该厂时序库对上。§7 的前置条件从「拿到这家厂的时序数据」降级为
「连上时序库，做一次 join 验证」。

### 9.3 教训

配对性结论必须**指名核对对象**。「配不上任何时序数据」是全称判断，
而实际证据只覆盖了一个数据集；写成「与某某评测数据集不配对」就不会误导后来者。

同类风险还有一条：**先在交付目录里把清单类文件翻一遍再下结论**。
推翻第一次结论的证据，一直就躺在同一个目录里。

## 10. 已知限制

- **管道连接拓扑未解**。只有几何走向，设备间连接关系需从坐标推导。
- **`clsid` 未建立类型名映射**。只统计了分布，未逐一命名图元类型。
- **zip 工程内的其他资产未调研**：`.slg`(248) / `.ssf`(218) / `.fbd`(95，功能块图) /
  `.pbc`(30) / `.dbm`(29) 未做分析。已探过各自的魔数，都**不是 SDFF**，
  要用本解析器读得先各做一次逆向：

  | 扩展名 | 魔数（前若干字节） | 初判 |
  |---|---|---|
  | `.fbd` | `24 00 02 00` + GUID | 功能块图，**最可能含整定参数**，优先级最高 |
  | `.pbc` | `serial DP cfg …` | 现场总线组态，与控制逻辑无关 |
  | `.dbm` | `pn_hardware_file` | 硬件配置，与控制逻辑无关 |
  | `.slg` / `.ssf` | 长度前缀 + 用户名 / `SUPCON FILE IN…` | 疑为画面的日志与签名边车文件 |

  > `LogicPic` 已不在此列——实测是 SDFF，零改动可解析，见 §6.4。
